# K-Chunran 분류체계 재설계안

작성일: 2026-09-17
상태: 설계안 — 코드 반영 전 검토용

## 1. 목적

현재 K-Chunran의 품종 데이터 구조를 실제 한국춘란 현장 분류에서 사용되는 명칭과 대조하여, 앞으로의 품종 도감·화예/엽예 분류·이미지 데이터셋·AI 형질 분석이 서로 충돌하지 않도록 데이터 구조를 재설계한다.

핵심 원칙은 다음과 같다.

1. 실제 현장에서 사용되는 분류명은 원형 그대로 보존한다.
2. 복합 분류명은 하나의 형질값으로 뭉개지 않고 구성 요소를 분해할 수 있게 한다.
3. 도감에서 보여주는 대표 분류와 AI 학습용 세부 형질을 분리한다.
4. 이미지 데이터는 현재 품종 JSON에 억지로 넣지 않고 별도 데이터셋으로 구축한 뒤 품종 ID로 연결한다.
5. 식물학적 taxonomy, 원예·감상 분류, 품종 정보, 이미지 형질 데이터는 서로 다른 층으로 관리한다.

## 2. 현재 K-Chunran과의 대조

현재 `categories.yml`은 `cultivar_class`, `leaf_form`, `pattern`, `leaf_tip`, `pattern_position`, `pattern_timing`, `market_status`로 구성되어 있다.

장점:
- 대표 분류와 세부 형질을 분리하려는 방향이 이미 잡혀 있다.
- 중투, 호, 복륜, 산반, 사피반, 호피반, 서반 등의 핵심 엽예 형질이 있다.
- 잎 형태와 잎끝 형태도 독립 축으로 분리되어 있다.

보완점:
- 화예품 축이 아직 없다.
- 소심, 홍화, 주금화, 황화, 자화, 백화, 두화, 원판화, 기화, 복색화, 색설화, 투구화, 수채화 등의 화예 용어가 구조화되어 있지 않다.
- `산반두화소심`, `중투복색소심`, `복륜복색화` 같은 복합 현장 명칭을 표현할 별도 계층이 없다.
- 엽예품에서도 `산반중투`, `서반중투`, `산반복륜`, `서산반`, `서호반`, `호반`, `감계열`, `다예품` 등 실제 분류 용어를 수용할 용어 사전이 부족하다.
- 현장 용어와 AI용 원자 형질을 구분하는 계층이 없다.

현재 세보 데이터는 `cultivar_class: jungtuho`와 `classification.pattern: jungtu`, `leaf_form: ipyeop`, `leaf_tip: dundu`처럼 기본 구조는 잘 맞는다. `images: []`도 이미지 데이터셋을 나중에 별도로 연결한다는 원칙에 따라 유지한다.

## 4. categories.yml 재설계 방향

현재 파일을 바로 교체하지 않고 다음과 같이 확장한다.

### 4.1 `cultivar_class`

도감에서 사용하는 대표 분류명. 한 품종의 대표 분류를 표시하기 위한 값이다.

### 4.2 `leaf_form`

단엽, 광엽, 입엽, 중엽, 중수엽, 환엽, 평엽 등 잎 형태를 관리한다.

### 4.3 `leaf_pattern`

중투, 호, 복륜, 산반, 사피반, 호피반, 서반 등 잎 무늬의 원자 형질을 관리한다.

### 4.4 `leaf_combination`

산반중투, 서반중투, 산반복륜, 서산반, 서호반, 호반 등 실제 현장 복합 명칭을 관리한다.

복합 명칭은 원자 형질과 연결되는 관계를 가져야 한다.

예:

```yaml
sanban_jungtu:
  name: "산반중투"
  components:
    - sanban
    - jungtu
```

### 4.5 `flower_color`

홍화, 주금화, 주홍화, 황화, 자화, 백화, 적화, 도화 등 꽃 색 계열을 관리한다.

### 4.6 `flower_form`

소심, 두화, 원판화, 기화, 투구화 등 꽃의 형태/화형을 관리한다.

### 4.7 `flower_pattern`

복색화, 색설화, 수채화, 호화, 복륜화, 산반화 등 꽃의 무늬·색설 관련 용어를 관리한다.

### 4.8 `flower_combination`

실제 현장에서 사용되는 복합 분류를 별도로 관리한다.

예:

```yaml
sanban_duhwa_soshim:
  name: "산반두화소심"
  components:
    pattern: "산반"
    flower_form: "두화"
    flower_type: "소심"
```

이 계층은 AI가 반드시 한 번에 예측해야 하는 클래스라는 의미가 아니라, 사람이 사용하는 분류명을 구조적으로 표현하기 위한 계층이다.

## 5. 품종 JSON 재설계 방향

현재 세보 구조를 폐기하지 않는다. 현재 구조를 기반으로 화예와 현장 용어 연결을 추가한다.

권장 예:

```json
{
  "id": "sebo",
  "name": "세보",
  "hanja": "世寶",
  "cultivar_class": "jungtuho",
  "classification": {
    "leaf_form": ["ipyeop"],
    "leaf_pattern": ["jungtu"],
    "leaf_combination": [],
    "leaf_tip": ["dundu"],
    "flower_color": [],
    "flower_form": [],
    "flower_pattern": [],
    "flower_combination": []
  },
  "field_names": [],
  "images": []
}
```

단, 실제 변경은 모든 기존 품종 JSON을 확인한 뒤 한 번에 하는 것을 권장한다.

## 6. 이미지 데이터셋은 별도 구축

사용자가 결정한 원칙에 따라 현재 품종 JSON의 `images: []`는 그대로 유지한다.

나중에 별도 이미지 데이터셋을 만든다.

```text
image_id
variety_id
source
image_type
original_url
local_path
bbox
leaf_or_flower
feature_labels
field_class
human_verified
verification_note
```

이렇게 하면 이미지가 많아져도 품종 JSON이 비대해지지 않는다.

## 7. 실제 구현 순서

### Phase 1 — 조사 원본 확보

1. 실제 춘란 사이트의 엽예품 분류 드롭다운 전체 수집
2. 실제 춘란 사이트의 화예품 분류 드롭다운 전체 수집
3. 분류명 원문 그대로 저장
4. 출처 URL과 수집일 저장
5. 여러 사이트에서 같은 용어가 어떻게 사용되는지 비교

### Phase 2 — 용어 정규화

1. 동의어/표기 차이 확인
2. 원자 형질과 복합 분류명 분리
3. 엽예/화예 축 분리
4. 복합명 → 구성 형질 관계 정의
5. `categories.yml` v2 설계

### Phase 3 — 품종 DB 연결

1. 기존 품종 JSON을 새 분류체계와 대조
2. 기존 `cultivar_class` 유지 여부 확인
3. 각 품종의 원자 형질 추가
4. 실제 현장 분류명과 연결
5. 출처 없는 값은 임의로 확정하지 않음

### Phase 4 — 이미지 데이터셋

1. 이미지 원본 수집
2. 품종 ID 연결
3. 엽예/화예 구분
4. bbox 및 세부 형질 라벨
5. 사람 검증
6. 학습 데이터셋 생성

### Phase 5 — AI

AI는 처음부터 복합 분류명을 직접 하나의 거대한 클래스 목록으로 학습시키기보다,

```text
이미지
 ↓
엽/꽃 구분
 ↓
원자 형질 추출
 ↓
형질 조합
 ↓
현장 분류 후보
 ↓
품종 후보
```

구조를 우선한다.

## 8. 현재 바로 다시 만들지 않아도 되는 것

- 기존 세보 품종 JSON 전체 교체
- 이미지 삽입
- 모든 분류를 즉시 코드에 추가
- AI 모델 구현
- 시장 가격 데이터 추가

먼저 실제 분류 원본을 더 확보한 후 한 번에 구조를 정리한다.

## 9. 다음 작업

가장 먼저 해야 할 일은 **실제 사이트의 드롭다운 분류 원본 수집**이다.

특히 다음 두 세트를 확보한다.

```text
등록품감상 → 엽예품 → 분류 드롭다운
등록품감상 → 화예품 → 분류 드롭다운
```

그 다음 현재 `categories.yml`과 대조표를 만들고, 그 결과를 바탕으로 `categories.yml v2`를 설계한다.

이 문서는 그 작업 전에 사용하는 설계 기준이며, 아직 기존 코드나 데이터를 변경하지 않는다.
